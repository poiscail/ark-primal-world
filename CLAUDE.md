# ARK: Primal World — contexte du projet (à lire en premier)

Jeu de combat d'orbes façon Dokkan Battle avec des dinosaures, **100 % local** (aucun compte, aucun serveur), en HTML/CSS/JS pur (pas de bundler). Depuis 0.18.0 le jeu est **uniquement sur PC** et livré en **application Windows (.exe)** construite avec Electron (`desktop/`). Plus de version téléphone ; les anciennes sauvegardes (navigateur, téléphone) s'importent toujours (Accueil > Sauvegarde).

- Dépôt : https://github.com/poiscail/ark-primal-world (branche `main`)
- Version actuelle : **0.30.0** (`game/js/00-version.js`, `ARK_VERSION` et `SAVE_FORMAT=1`)
- L'utilisateur est français : **répondre en français**, être honnête sur ce qui est testé (jamais affirmer qu'une chose non testée marche ; l'.exe Windows n'est testé que par la construction automatique GitHub sur une machine Windows virtuelle ; équilibrage mesuré par simulation seulement).
- Attentes permanentes : améliorer sans cesse le gameplay, les animations et les graphismes ; mettre à jour GitHub à la fin de chaque étape ; l'utilisateur dira à la fin ce qu'il veut retirer (ne rien supprimer sans demande).
- Deux sessions ont travaillé en parallèle le 15/10/2026 (branche `main` 0.13→0.17 et branche `claude/magical-heisenberg-a3w1xx` avec une autre 0.13) ; 0.18.0 les fusionne. Toujours `git fetch` et regarder `origin/main` avant de commencer.

## Lancer / tester / construire
```
open game/index.html                 # jouer directement dans un navigateur (développement)
python3 tools/build.py               # .exe portable + installateur (sur Windows ; hors Windows il faut Wine)
python3 tools/build.py --linux --electron-zips=DOSSIER   # version Linux dépaquetée pour tester l'application ici
python3 tools/build.py --stage       # copie seulement game/ dans desktop/app/ (puis « npm start » dans desktop/)
tools/run_tests.sh                   # 42 suites Playwright (python3, chromium headless) ; ~8-10 min
python3 tests/test_balance.py        # simulations d'équilibrage (lentes, à lancer en tâche de fond)
python3 tests/test_balance_modes.py
python3 tests/test_balance_maze.py 10   # labyrinthe : courses complètes par un bot (~5-15 min)
python3 tests/test_balance_nightmare.py 20   # mode Cauchemar (option : pv atq k b pour essayer des réglages)
python3 tests/test_balance_trials.py 20      # épreuves de la meute, par palier
```
- Tests : Playwright Python (ici `pip install playwright==1.56.0`, version qui correspond au Chromium préinstallé dans /opt/pw-browsers). Les tests coupent animations/dialogues (`setPref("anim",false)`, `setPref("lore",false)`) car sinon les simulations de milliers de combats sont très lentes. **Chaque test doit finir par `sys.exit(1 if FAILS else 0)`** (sinon `run_tests.sh` ne voit pas les échecs). `dist/` est ignoré par git. Les scripts longs (>2 min) doivent tourner en arrière-plan.
- Application : `desktop/main.js` (fenêtre, F11, une seule instance, sauvegarde dans `%APPDATA%\ARK Primal World`), `desktop/preload.js` (pont `window.arkDesktop` : `toggleFullscreen`, `quit`, `info`), `game/js/99-desktop.js` (panneau « Application Windows » des réglages). Test de lancement : `"ARK Primal World.exe" --smoke-test --smoke-data=DOSSIER --smoke-expect-boot=N --smoke-out=f.json --smoke-shot=f.png` (combat joué, invocation + vrai clic sur OK, sauvegarde conservée entre 2 lancements ; jamais la vraie sauvegarde).
- **Publier une version** : `ARK_VERSION` + section `## X.Y.Z — titre` en tête du CHANGELOG (elle devient la page de la version), tests verts, envoi sur `main` → `.github/workflows/windows-exe.yml` construit et teste l'installateur et le portable sur Windows, puis `tools/releases.py` publie la page `vX.Y.Z` avec les .exe (« dernière version ») et crée une fois pour toutes les pages des anciennes versions (`HISTORY` : version → commit de main, zip navigateur joint). Lien permanent : https://github.com/poiscail/ark-primal-world/releases/latest (README + bouton « Dernière version » des réglages, `ARK_RELEASES`). Sur les branches `claude/**`, le workflow construit et teste seulement (fichiers dans les artefacts). Suivi des exécutions : outils MCP GitHub (`actions_list`, `get_job_logs`) ou l'API publique `https://api.github.com/repos/poiscail/ark-primal-world/actions/runs/<id>` avec curl.
- Ici (conteneur Linux, root) : Electron exige `--no-sandbox` et un écran virtuel (`xvfb-run -a`). Le téléchargement d'Electron par npm échoue derrière le proxy : récupérer `electron-v<ver>-linux-x64.zip` / `win32-x64.zip` + `SHASUMS256.txt` avec curl depuis les releases GitHub d'Electron, vérifier le sha256, puis `--electron-zips=DOSSIER`. Pas de Wine ni de makensis : les .exe Windows sont construits et testés par `.github/workflows/windows-exe.yml` (windows-latest).

## Architecture (voir docs/ARCHITECTURE.md)
Les scripts sont chargés dans l'ordre de `game/index.html` et **se corrigent les uns les autres par « monkey-patching » en portée globale** : `const _x=fn; fn=function(){...}`. Règles :
- Ne jamais déclarer `const` un nom destiné à être re-patché (`function` ou `let`). Deux scripts qui déclarent le même `let`/`const` global = erreur de syntaxe, le second script ne se charge pas du tout.
- **L'ordre des `<script>` et des `<link>` fait partie du contrat.** `css/95-theme.css` puis `96-skins.css` restent les derniers thèmes ; `90-platform.css` après, puis `97-pc.css` (mise en page PC), `97-juice.css`, `97-content.css`, `97-maze.css`, `97-nightmare.css`, `97-trials.css`, `97-far.css`, `97-nest.css`, `97-player.css`, `97-combat2.css`, `97-combat3.css` puis `97-combat4.css` en tout dernier. `99-layout.js` reste le dernier script (`99-juice.js` juste avant).
- Les modules ajoutent leurs champs de sauvegarde via un wrapper de `ens()` (migration/initialisation).
- État `S` dans `localStorage["arkPrimalMobile"]` (nom historique, ne pas changer) ; config admin `arkPrimalConfig` ; préférences `arkPrimalPrefs` (`PREFS` : sound, vol, music, anim, lore, chain, diff, art, theme, skin, auto, spd ; `vib` n'a plus d'effet) ; sauvegardes auto `arkPrimalBackups`.
- Enveloppe de sauvegarde `{game:"ark-primal-world",fmt:1,ver,at,from,S,cfg}` ; codes `ARK2.`(gzip+base64) / `ARK1.` / base64 ancien ; `validate()` strict ; import = copie « avant import » puis rechargement. `ARK_PLATFORM` vaut toujours `"pc"`.

## Pièges connus
- `T3` et `alive` sont des `const` : inaccessibles via `window.T3` ; utiliser `S.team.slice(0,3)`.
- `SK_of` est `const` (compétence lue sur `SPEC[type].sk`).
- `renderBattle` est réassigné par ~15 modules ; l'ordre compte. `stageBuild()` est appelé depuis 94-battle-anim juste après le rendu de base ; les modules ultérieurs cherchent `.sHud`/`.sFig` (avec repli sur l'ancien `.panel`).
- `giveXP`/`give()` : `give` gère matériaux (`S.mat`) ou champs de `S` (tickets, shards…).
- Comparer deux états après transfert : appeler `ens()` avant (champs par défaut ajoutés).
- Tester les boutons par de **vrais clics** Playwright (pas seulement en appelant la fonction) : une couche d'effets peut intercepter les clics (bug du bouton OK d'invocation, corrigé dans les deux branches).
- Sous-onglets (99-nav) : un bouton d'un autre sous-onglet est caché (`.subhide`) ; dans un test, ouvrir d'abord son sous-onglet (clic sur `#subnav button[onclick="subSet('summon','bonus')"]`, voir `show()` dans `test_summon_buttons.py`).
- Fenêtre minimale de l'application : 1024×640 (`desktop/main.js`) ; le combat doit y tenir sans défiler (règle compacte `max-height:760px` dans `94-layout.css`). `test_layout.py` vérifie 1280×800, 1366×700 et 1920×1080.
- Éviter les `sleep` enchaînés pour attendre des tests ; utiliser un `until` avec timeout.
- Combat : ne jamais déplacer les nœuds de `#battleArea` ; `99-layout.js` (dernier script) les étiquette `bl-*` et `css/94-layout.css` règle l'ordre (grille 2 colonnes). Un nouvel élément non reconnu par `blKind()` va en fin d'écran.
- Animations de combat : délais via `fxd(ms)` (vitesse `FX_SPEED`, `let` dans 94), effets dans `#fxLayer` via `fxAdd`. Une compétence n'anime que son lanceur (`BQ.sk` → `castFx`) ; orbes/super → `atkFx` par famille (`PORT[type][0]`) ; riposte ennemie jouée après 480 ms (`foeFx`).
- `eye()` (portraits) est remplacé temporairement pendant `corruptSVG` (yeux luisants) : les portraits du joueur restent identiques (testé).
- Noms et variété des ennemis appliqués à l'affichage (`bnName`/`cxVary` dans `stageBuild`), car `startBattle` peut être différé par un dialogue d'histoire (dans l'application, `navigator.webdriver` est faux : couper `lore` pour un test automatique).
- Trait « Carapace » (dès le niveau 8, aléatoire) : un coup peut être absorbé à 0 → dans les tests de dégâts, niveau < 8 ou `e.tr="";e.sh=0`.
- Tests d'effets : compter les ajouts au `#fxLayer` (MutationObserver) plutôt que le nombre net d'enfants (les effets précédents disparaissent en même temps).
- Coupure de super attaque : `special()` est différé de ~1,25 s (÷ vitesse) quand les animations sont actives ; désactivée sous `navigator.webdriver` sauf `window.__forceCutin` (comme les dialogues) ; dans l'application (Electron) elle est active. Pendant la coupure, `tapOrb`/`useSkill` ne font rien.
- Secousse et parallaxe utilisent les propriétés CSS `translate`/`rotate` (indépendantes de `transform`) : ne pas poser d'autre `translate` sur `.battlestage`, `.sc-layer`, `.sTeam`, `.sEnemy`, `.heroDino`. Le gel `hitStop()` ne met en pause que les animations « running » de `#battleArea`/`#fxLayer` (relancer une animation terminée la rejouerait).
- Mise en page PC : la navigation `.bottomnav` est une colonne fixe à gauche (`--rail`) ; pour « le bas de l'écran » dans un test, prendre `innerHeight` si la barre est verticale (voir `test_layout.py`).
- Chef/liens : bonus appliqués au premier rendu du combat (`tmApply` dans le wrapper de `renderBattle`), car `startBattle` peut être différé (dialogue) et les modes (80-modes) créent d'abord un combat d'histoire puis le transforment (`f.o`, `f.zone`, `f.enemies` changent ensuite) : tout ce qui dépend du mode doit être calculé paresseusement (voir `wxOf`).
- Labyrinthe : PV de course = rapport par place (`S.maze.run.hp`), enregistré à chaque rendu d'un combat du labyrinthe (`f.mzOn`) et appliqué par `mzSetup` après `tmApply` (chef/liens). Combat via `MODES.maze`, victoire via `eventWin` remplacé, défaite via `settleLose` remplacé. Relancer la même case reprend le combat en cours (même `key`) : dans un test, `fight=null` avant `mzFight()` pour un nouveau combat. Les combats normaux commencent à la vague 2 (`f.mzW0=1`, 2 ennemis) : titre et bannières renumérotés. Niveau des ennemis : `mzN0()` = progression d'histoire ou 2×(niveau moyen de l'équipe − 1) si plus haut.
- Objets : lire l'attribut d'un objet avec `paOf(it.pa)` (70-equipment), jamais `PA[it.pa].i` : au chargement, la sacoche et le sac s'affichent avant que `99-species2` déclare ses attributs (erreur réelle trouvée par test_nightmare, 0.24).
- Nouvelles compétences (0.24) : le moteur de base (switch de `useSkill`) ne les connaît pas ; `99-species2` calcule l'effet avant d'appeler `useSkill`, pose `f._skx={dmg,msg}` que son wrapper d'`afterAction` ajoute aux dégâts (avant les carapaces de `99-enemy-traits`). Ce module doit rester avant `99-trials` (« sans compétences » prioritaire). Durées (`f.ewk`, `f.taunt`, `f.rly`) décomptées dans son wrapper d'`enemyTurn` ; `f._bigNow` signale une attaque puissante pendant ce tour (Écailles épaisses).
- Épreuves : un combat d'épreuve est refusé si l'équipe n'est pas conforme (`trTeamOk`) ; « Former l'équipe » réordonne `S.team` et mémorise l'ancienne tête (`S.trial.prev`). Règles : `nosuper` (jauge remise à 0 à chaque rendu, sinon l'auto-combat appellerait `special()` en boucle), `noskill` (recharges à 99), `timed` (`f.trAct` compte orbes + super, défaite via `settleLose`). Une victoire hors de l'écran de combat ne redessine pas `#battleArea` (normal) : dans un test, revenir sur `go("battle")`.
- Cauchemar : bouton Normal/Cauchemar dans l'écran Histoire (`nmView`, enveloppe de `renderStory` qui remplace `#chapters`, bannière modifiée par `nmBanner`) ; un chapitre s'ouvre quand son gardien normal est battu (`nmOpen`). Victoire via `eventWin` remplacé (comme le labyrinthe).
- Espèces exclusives (0.25, `SPEC[k].ex`, `isEx(k)`) : exclues de `pickType`, `featured`, `pullEl` (la pitié est restaurée en cas de nouveau tirage), `shopBuy`, `offerBuy` et des lignes de la boutique de fragments. Une nouvelle source d'invocation doit aussi les filtrer. Elles s'obtiennent à la première victoire contre un gardien du Grand Nord (`farWin`).
- Grand Nord : `stageZone` teste « abysse » avant « toundra/glac » (sinon les abysses prenaient le décor de la toundra) ; les dialogues `far*` ne s'affichent qu'une fois (`S.far.lore`).
- Nid d'élevage (0.26) : le résultat (espèce, gènes, mutation, variante, génération, niveau) est fixé à la ponte dans `S.nest.slots[i]` ; dans un test, mettre `S.nest.slots[i].t1` dans le passé pour l'éclore. Les gènes et l'empreinte multiplient le résultat final de `stats` (wrapper chargé après l'équipement et le rang). L'empreinte monte dans un wrapper de `win` (les 3 dinos de `T3()`, `d.baby`). Les exclusives (`SPEC[k].ex`) ne pondent pas. Le compte à rebours met à jour le texte chaque seconde sans redessiner l'écran (sinon les clics se perdent).
- Événements (0.26) : `EVENTS` a 8 entrées ; les 4 nouvelles ont été ajoutées à la fin pour que l'événement de la semaine en cours ne change pas (semaine `wkNow()` 2963 : 2963 % 8 = 2963 % 4). Effets portés par l'événement : `zn` (décor, via `stageZone`/`BZONE.events`), `nest` (incubation), `ess` (essence). Dans un test, échanger l'événement courant avec celui voulu puis le remettre (voir `SWAP`/`UNSWAP` dans `test_nest.py`).
- Règles du Défi du jour (0.26) : `dchInfo()` renvoie aussi `rule` (`DRULE_FORCE` pour un test). Blessures profondes : plafond de PV `f.hpCap` posé après le premier rendu (chef et liens appliqués), appliqué avant le tour ennemi et à chaque rendu.
- Dresseur (0.27) : l'écran de victoire a deux `.result` dans `#battleArea` (le journal `bl-log` d'abord) : viser `.result > .rarity` ; ses enfants ont un `order` CSS, donc tout ajout copie l'`order` du voisin. Les images PNG passent par un SVG dessiné dans un canvas puis un lien `download` (Electron : `will-download` de `desktop/main.js`).
- Combat I (0.28) : `f._spX` est pris par la règle Surcharge (99-events2) ; 99-combat2 utilise `f._sup2`. La Garde appelle `afterAction(0,…,true)` : le tour ennemi a lieu tout de suite, avec `f.guard` (dégâts ×0,5), remis à 0 après `enemyTurn`. La rage ne monte qu'avec les orbes (`f._tap`) ; la furie est décidée au début d'`enemyTurn`.
- Combat II (0.29) : le terrain est choisi au premier rendu (`c3PickTer`, 30 %, pas en Arène/Raid/Défi/Épreuves) ; les objets clignotent par une lueur (pas de déplacement, sinon Playwright juge le bouton « instable » et refuse le clic). La faiblesse vient du nom de créature (`hashS(cxKey)`), connue si `S.foes[clé]`.
- Décisions « au premier rendu » (terrain, duo, plateau 4×4) : les modes de `MODES` créent d'abord un combat d'histoire puis changent `f.o` ; ces décisions sont donc refaites quand `f.o` change (`f.terSet`/`f.c4Set` gardent l'objet `f.o` vu). Duo : la cible est `f.wave` (0 ou 1) ; `killEnemy` range les deux premiers ennemis pour que la vague suivante soit le survivant. 4×4 : `f.orbs` reçoit un `filter` propre (non énumérable) qui ramène les comptes à 9 cases pour `boostOf` (const de 92-orbs-fx, non remplaçable).
- Anti-enlisement (0.25, `99-species2`) : à partir de `STALL_T=40` actions sur la même vague (`f.turn`, remis à 0 par `killEnemy`), l'ennemi prend `e.stall`, perd son trait et gagne +20 % d'ATQ toutes les 5 actions (pas dans le Raid, `f.raid`). Un test qui pose `f.turn` à la main doit en tenir compte.
- Les modes de `MODES` (Tour, Arène, Événements, Labyrinthe) refont la bannière d'ouverture après avoir transformé le combat d'histoire de base (avant 0.21 elle affichait « Niv. N · zone »).
- Simulations d'équilibrage : `WX_ON=false` (la météo change chaque jour) ; fixer `S.level` (rang du joueur, +0,5 % PV/ATQ par rang) avant chaque combat ; sinon il grimpe pendant la simulation et fausse les dernières mesures.
